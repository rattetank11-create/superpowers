# CS2 Demo Analyzer

Сайт для разбора механики по демке CS2. Пользователь загружает `.dem`, выбирает себя из 10 игроков матча и получает отчёт: контрстрейфы, дуэли, crosshair placement, трейды, рекомендации и оценку уровня FACEIT. У каждого отчёта есть своя ссылка, которой можно поделиться. Сама демка удаляется с сервера сразу после анализа, хранятся только результаты.

```
cs2-demo-analyzer/
├── backend/                 FastAPI + RQ-воркер + модуль анализа
│   ├── analysis/            метрики (каждая — отдельный модуль с тестами)
│   │   ├── loader.py          чтение демки через demoparser2
│   │   ├── counterstrafe.py   контрстрейфы
│   │   ├── duels.py           дуэли, точность, базовая статистика
│   │   ├── crosshair.py       crosshair placement
│   │   ├── trades.py          трейды
│   │   ├── recommendations.py rule-based советы
│   │   ├── rating.py          оценка ELO / уровня FACEIT
│   │   ├── pipeline.py        сборка отчётов для всех игроков
│   │   └── config/            пороги, оружие, модель ELO, уровни FACEIT, тексты
│   ├── app/                 HTTP API, БД, очередь, загрузка чанками
│   ├── scripts/calibrate_elo.py
│   └── tests/
├── frontend/                Next.js (TypeScript) + Tailwind, интерфейс на русском
├── docker-compose.yml       caddy + web + api + worker + postgres + redis
├── Caddyfile                HTTPS и маршрутизация /api → backend
└── .env.example
```

## Быстрый старт (Docker)

```bash
cp .env.example .env          # задайте POSTGRES_PASSWORD
docker compose up -d --build
```

Откройте https://localhost. Для `localhost` Caddy выпускает локальный сертификат, поэтому браузер покажет предупреждение — это нормально.

## Разработка без Docker

Нужны Python 3.12+, Node 22+ и Redis. Без Redis тоже можно — в режиме `TASK_MODE=inline`.

```bash
# backend
cd backend
python -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
TASK_MODE=inline uvicorn app.main:app --reload --port 8000
# или с очередью: redis-server & ; rq worker analysis & ; uvicorn app.main:app --port 8000

# frontend (в другом терминале)
cd frontend
npm install
npm run dev                     # http://localhost:3000, /api проксируется на :8000
```

В режиме `inline` анализ идёт в процессе API: так проще отлаживать, но в проде нужен `rq`.

### Тесты

```bash
cd backend
pytest                                            # юнит-тесты метрик и API
CS2_TEST_DEMO=/path/to/match.dem pytest           # + интеграционные тесты на реальной демке
cd ../frontend && npm run typecheck && npm run build
```

## Деплой на Ubuntu VPS

Минимум: 2 vCPU и 4 ГБ RAM. Парсинг 500-мегабайтной демки занимает до 1–2 ГБ памяти.

1. **DNS.** У регистратора домена создайте A-запись `example.com → IP_VPS`. Для www — ещё одну A-запись или CNAME.
2. **Docker:**
   ```bash
   sudo apt update && sudo apt install -y ca-certificates curl git
   curl -fsSL https://get.docker.com | sudo sh
   sudo usermod -aG docker $USER && newgrp docker
   ```
3. **Файрвол:** откройте только SSH и веб.
   ```bash
   sudo ufw allow OpenSSH && sudo ufw allow 80/tcp && sudo ufw allow 443/tcp && sudo ufw allow 443/udp
   sudo ufw enable
   ```
4. **Код и настройки:**
   ```bash
   git clone <репозиторий> cs2 && cd cs2/cs2-demo-analyzer
   cp .env.example .env
   nano .env        # DOMAIN=example.com, POSTGRES_PASSWORD=<длинный случайный>
   ```
   Пароль можно сгенерировать так: `openssl rand -base64 32`.
5. **Запуск:**
   ```bash
   docker compose up -d --build
   docker compose ps          # все сервисы Up, api — healthy
   docker compose logs -f caddy   # видно, как выдаётся сертификат
   ```
   Caddy сам получит сертификат Let's Encrypt и будет его продлевать. Порты 80 и 443 должны быть доступны снаружи. Чтобы получать письма о сертификатах, раскомментируйте блок `email` в начале `Caddyfile`.
6. **Обновление:** `git pull && docker compose up -d --build`.
7. **Бэкап результатов:**
   ```bash
   docker compose exec -T db pg_dump -U cs2 cs2 | gzip > backup-$(date +%F).sql.gz
   ```

Логи: `docker compose logs -f api worker`. Если воркер падает по памяти, увеличьте `WORKER_MEM_LIMIT` или RAM сервера.

## Как считаются метрики

Все пороги лежат в `backend/analysis/config/thresholds.toml`, параметры оружия — в `weapons.toml`. Код менять не нужно.

Названия полей проверены на реальной демке CS2 (demoparser2 0.42):
- `velocity_X/Y/Z` в SourceTV-демках пустые, поэтому скорость берём из `velocity` — это горизонтальная скорость по позициям.
- `buttons` — битмаска. Биты проверены по направлению движения: W=8, S=16, A=512, D=1024, Shift=65536.
- `approximate_spotted_by` (серверный `m_bSpottedByMask`) содержит SteamID врагов, которые видят игрока.
- `pitch > 0` — взгляд вниз. На хедшотах ошибка угла до головы получается меньше 1°, что подтверждает конвенцию.
- `player_hurt` приходит в тот же тик, что и `weapon_fire`.

**Контрстрейф.** Берётся первый выстрел каждой очереди: новая очередь начинается после паузы больше 0,5 с или при смене оружия. Скорость в момент выстрела сравнивается с порогом точности — 34% от максимальной скорости оружия; в прицеле используется скорость в прицеле. Категории: perfect / slow / moving / air.

Тайминг определяется по нажатым кнопкам. Начало торможения — тик, после которого клавиши перестали толкать игрока по направлению движения. Если противоположная клавиша нажата в течение 4 тиков, это `counter`, иначе `release`. Выстрел до того, как скорость упала ниже порога, — `early`. Ожидание после остановки дольше 6 тиков (~94 мс) — `late`. Если кнопок в демке нет, начало торможения берётся по пику скорости. «% идеальных» считается только по выстрелам после движения; выстрелы с места в него не входят.

**Дуэли.** Дуэль — обмен уроном между двумя игроками с паузами не больше 3 с. Результат: win, loss или none. Opening — дуэль, в которой произошло первое убийство раунда. «Стрелял первым» — у кого раньше был выстрел с углом до головы соперника ≤ 12°. TTK — время от первого такого выстрела до убийства. «Пик» — игрок двигался быстрее соперника перед первым попаданием. «С флешкой» — соперника ослепил тиммейт за 3 с до дуэли. Точность первой пули — доля первых выстрелов очереди, которые попали во врага в тот же тик.

**Crosshair placement (приближение).** Угол между прицелом и головой врага (позиция + высота глаз) в момент, когда сервер пометил врага как видимого для игрока (`m_bSpottedByMask`). Это не точный raycast, поэтому в отчёте метрика помечена как приближение.

**Трейды.** Смерть считается разменянной, если убийцу убил тиммейт в течение 5 с. Убийство — размен, если жертва за 5 с до этого убила тиммейта.

## Рекомендации

`analysis/recommendations.py` — набор правил вида «метрика хуже порога и данных достаточно → совет». У каждого правила есть секция `[recommendations.<id>]` в `thresholds.toml`: `threshold`, `min_samples`, `severity`. Тексты лежат в `config/locales/ru.json`. Приоритет = severity × (1 + относительное отклонение от порога). Три самых приоритетных совета выводятся вверху отчёта.

## Реальный ELO с FACEIT и поправка по игре

Игроку ничего вводить не нужно. После анализа воркер ищет на FACEIT аккаунты всех 10 игроков:

1. По SteamID64 из демки: `GET https://open.faceit.com/data/v4/players?game=cs2&game_player_id=<steamid>`.
2. Если не нашлось — по нику из демки: `GET /players?nickname=<ник>`. Результат принимается **только** если в профиле привязан тот же SteamID: ники в демке и на FACEIT часто расходятся.

Из ответа берутся ник, аватар, ссылка на профиль, `games.cs2.faceit_elo` и `games.cs2.skill_level`. Результат кэшируется в Redis на `FACEIT_CACHE_SECONDS`. Кнопка «Обновить» в отчёте (`POST /api/reports/{id}/faceit/refresh`) ищет заново, без кэша, и ограничена по частоте.

**Ключ API.** Зайдите на https://developers.faceit.com, создайте приложение и в нём ключ типа **Server side**. Запишите его в `.env` как `FACEIT_API_KEY=...` и перезапустите: `docker compose up -d`. Ключ используется только на сервере и во фронт не попадает.

**Проверить реальный ответ API** (названия полей взяты из документации FACEIT Data API v4; их стоит сверить на своём ключе):

```bash
docker compose exec api python -m scripts.faceit_probe 76561198000000000 --nickname SomeNick
```

Скрипт печатает сырой JSON и то, как его разобрал клиент (`app/faceit.py`, функция `parse_player`). Если FACEIT изменит формат, правка нужна только в `parse_player`.

**Если FACEIT недоступен** (нет ключа, таймаут, ошибка API), анализ не ломается: в отчёте показывается оценка по метрикам с пометкой. Если аккаунт не найден — пометка «Аккаунт FACEIT не найден».

### Поправка ELO по игре

База — текущий ELO с FACEIT. Игра оценивается **относительно уровня игрока**: для 2500 ELO средняя игра — уже плохая.

```
perf = (ELO, которое показывают метрики этой демки − текущий ELO FACEIT) / scale    (scale = 350)
```

| Уровень | Условие | Поправка |
|---|---|---|
| Игра в ноль (`very_bad`) | perf < −1.5, или 0 убийств, или ADR < 25 | −300 … −700 |
| Плохая игра (`bad`) | −1.5 ≤ perf < −0.25 | −100 … −300 |
| Нормальная игра (`normal`) | perf ≥ −0.25 | +100 … +300 |

Внутри уровня поправка интерполируется по perf: чем хуже игра, тем ближе к краю диапазона. За краями значение ограничивается. Итоговый ELO не опускается ниже 100, уровень берётся из `faceit_levels.json`. Все числа лежат в секции `[faceit_adjustment]` файла `thresholds.toml`, логика — в `analysis/rating.py: adjust_faceit_elo`.

Это оценка по одной демке, а не реальное изменение ELO на FACEIT. «ELO по метрикам» берётся из модели ниже; пока она не откалибрована, поправка тоже приблизительная.

## Оценка уровня FACEIT

Диапазоны ELO по уровням лежат в `config/faceit_levels.json`. Источник — [официальная страница FACEIT](https://support.faceit.com/hc/en-us/articles/10525200579740-FACEIT-CS2-Elo-and-skill-level), проверено 14.10.2026: 1: 100–500, 2: 501–750, 3: 751–900, 4: 901–1050, 5: 1051–1200, 6: 1201–1350, 7: 1351–1530, 8: 1531–1750, 9: 1751–2000, 10: 2001+.

Модель линейная: `ELO = intercept + Σ weight × z(признак)`. Веса лежат в `config/elo_model.json`. Сейчас это **априорные веса**, выставленные вручную, и в отчёте так и написано. Сайт показывает диапазон ±`residual_std`. Если каких-то признаков не хватает или демка короткая, диапазон расширяется.

### Калибровка

Соберите CSV с демками, где известен ELO игроков:

```csv
demo_path,steamid,elo
/data/demos/match1.dem,76561198000000001,1850
/data/demos/match1.dem,76561198000000002,1320
```

```bash
cd backend
python -m scripts.calibrate_elo dataset.csv --dry-run   # посмотреть веса и ошибку
python -m scripts.calibrate_elo dataset.csv             # записать config/elo_model.json
```

Скрипт извлекает признаки той же функцией, что и сайт, и кэширует их в `dataset.features.json`. Модель — ridge-регрессия; ошибка leave-one-out становится шириной диапазона. Чтобы применить новые веса, пересоберите api/worker. Нужно хотя бы несколько сотен игроков с разным уровнем.

## Безопасность и ошибки

- Файл проверяется по заголовку: `PBDEMS2\0` — CS2, `HL2DEMO\0` — CS:GO, их отклоняем с отдельным сообщением. Первый чанк проверяется сразу, до загрузки остального файла. Расширение и размер проверяются при создании загрузки, размер каждого чанка — при приёме.
- Rate limit на новые загрузки по IP (Redis). Upload ID — случайный UUID.
- Понятные ошибки: битая демка (`corrupt_demo`), не CS2 (`not_cs2`), не демка (`not_a_demo`), нет раундов (`no_rounds`), игрок не найден (`player_not_found`), таймаут анализа.
- Брошенные чанки удаляются через `UPLOAD_TTL_MINUTES`, забытые демки — через 6 часов.

## Известные ограничения

- `counterstrafe.py` (прототип) не попал в репозиторий. Модуль контрстрейфов написан заново по ТЗ. Если пришлёте прототип, можно сверить логику и перенести удачные решения.
- Поле «ссылка на демку» пока выключено (помечено «скоро»).
- Веса ELO не откалиброваны, пока нет датасета. От них зависит и поправка к реальному ELO.
- Поля ответа FACEIT API взяты из документации, на живом ключе не проверены (из среды разработки FACEIT был недоступен). Сверьте их с помощью `scripts/faceit_probe.py`.
- Схема БД создаётся через `create_all`. Перед изменением моделей стоит подключить Alembic.
